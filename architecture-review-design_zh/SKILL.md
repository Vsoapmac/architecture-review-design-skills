# 架构评审与设计

## 概述

本技能包含两种模式：**评审现有架构** 和 **设计新架构**，两者共用一套 8 维度质量框架：

1. **功能正确性** — 模糊的需求能否被精准实现？
2. **可移植性** — 换一个平台/环境，需要改多少代码？
3. **可扩展性 / 可维护性** — 新功能/新业务/业务调整需要改几个文件？
4. **可观测性** — 半夜出问题，多快能定位到？
5. **可测试性** — 功能拆开来测试方不方便？
6. **易用性** — 新人接手，10 分钟内能跑通核心流程吗？
7. **性能 / 可伸缩性** — 数据量/并发量翻 10 倍，架构会变形吗？
8. **安全性** — 发生安全泄露或攻击，影响面多大？

评审模式：先对话式深入，最终交付"打分报告 + 现状（As-Is）架构文档"；设计模式：以需求澄清为驱动，交付目标（To-Be）架构文档。两种模式共享同一套维度定义、同一套架构视图清单，以及同一种单文件 HTML 交付格式。

## 何时使用

| 场景 | 示例触发语 |
|------|-----------|
| 评审现有代码库 | "架构评审"、"评审一下这个项目的架构"、"架构体检"、"帮我看看这个架构" |
| 设计新系统 | "架构设计"、"帮我设计系统架构"、"帮我设计一个 xxx 系统" |
| 评审设计方案 | "这个设计方案靠谱吗"、"帮我评估一下这份设计" |
| 只梳理现状架构（不打分） | "帮我梳理这个系统的架构"、"还原一份架构文档"（见工作流 A 的"只出架构文档的变体"） |

不适用场景：纯业务问题、单函数改动、文件级别的代码评审（见"边界规则"）。

## 第 0 步 — 输出语言（动手之前先问）

在流程最开始一次性问清：

> "文档用什么语言？中文 / English（将统一用于正文、图表标签、表格与 HTML 菜单）"

规则：

- **整份交付物只有一种语言**：对话摘要、正文、标题、表头、元信息标签、Mermaid 节点标签/泳道名/连线标签、图注，以及 HTML 菜单。中文文档配英文菜单（或反过来）都算失败产物——验收清单里会逐项检查。
- 这个答案同时决定用哪套模板大纲（`design-doc-template.md` §A 英文 / §B 中文）和生成器参数（`md2html.py --lang`）。
- 它同样决定对话语言：讨论发现的问题也用同一种语言。
- 中途换语言就整份重写，不要只翻译一半。
- 用户若已声明过语言偏好，用一句话确认即可，不必重复问。

## 共享基础（任何流程开始前先读）

开始任何评审或设计之前，先读取：

1. **`references/8-dimensions.md`** — 8 个维度的权威定义：核心问题、评估问题集、检查要点、常见反模式、整改建议，以及 0-5 分评分规则。
2. **`references/mermaid-spec.md`** — 视图清单：五类必需视图（系统上下文 / 组件图 / 分层图 / 运行时图 / 数据流图）+ 按触发条件的视图（部署图 / 状态机图 / 数据模型）与一个按需视图（泳道图，§3.4），各自的画法规则，以及硬一致性规则（§8）。输出任何架构图都必须遵守，并配合 **`references/html/check_views.py`**（这些规则的可执行校验）。
3. **`references/html/html-output-spec.md`** — HTML 产物规范（仅在生成/保存 HTML 时读取）：语言与界面文案（§3）、组件类名注册表与章节映射（§5）、图形缩放/全屏规则（§8）、手写 tier 的令牌规则（§10）、验收清单（§11）。

输出 HTML 时，还必须使用技能包内 `references/html/` 下的 `report-shell.html`（骨架，界面双语，图形缩放已内置）与 `md2html.py`（生成器，纯标准库）。

不要凭记忆编造维度定义——一律以参考文件为准。也不要自己随手决定画哪些图：视图清单是交付契约的一部分，由 `check_views.py` 强制执行。

## 工作流 A：架构评审

### 第 1 步 — 项目侦察

扫描项目：目录结构、README、配置文件、依赖清单、主要源码分布。大型项目先让用户划定评审范围（单文件、单模块或某个子系统）。不要默认全仓库扫描。

侦察结果同时喂给两条线：第 4 步的打分，以及第 4 步的"现状架构视图"——记下能证明结构的关键路径（入口、模块边界、存储配置、调用链）。

### 第 2 步 — 维度裁剪

询问用户哪些维度最重要。默认跑全部 8 个，但允许裁剪——例如小型命令行工具可以跳过"性能/可伸缩性"。深入前先确认最终维度清单。

### 第 3 步 — 对话式深挖（一次一个维度）

对每个选定维度：

1. 先问用户的主观感受："维度 X，你觉得有没有隐患？"——先收集用户的视角。
2. 再用 `8-dimensions.md` 中该维度的检查要点，结合代码/文档找证据。
3. 逐条讨论发现的问题，并分级：
   - 🔴 **必须修复** — 阻碍正确性、安全性或后续开发
   - 🟡 **建议修复** — 明显痛点，成本中低
   - ⚪ **仅供参考** — 信息性，可选
4. 当前维度讨论完再进入下一个。不要一次性倾倒所有发现。

### 第 4 步 — 打分报告 + 现状架构

交付物是**"这个系统今天的架构文档"加上评估结论**，而不只是一张评分表。按 `references/review-report-template.md`（对应语言的大纲）汇总：

1. **总览** — 8 维度雷达总览表（每项 0-5 分 + 一句话结论，驱动雷达图）
2. **系统架构（现状）** — 按 `mermaid-spec.md` §1 输出**五类必需视图**（系统上下文、组件图、分层图、带失败分支的运行时图、数据流图），外加所有触发条件成立的条件视图（部署图、状态机图、数据模型）。每张图都要有一句"看图重点"，**并注明取证来源**（结构是从哪些路径读出来的）。把分层图并入组件图必须显式写明"因……合并"；确实画不出的必需视图保留标题并写一行"不适用的原因：……"。**图里暴露出的缺陷，正文必须点名**——否则画出来的东西读起来就像设计本意。
3. **各维度详情** — 评分、证据（文件路径/行号/代码片段）、问题清单及优先级
4. **整改路线图** — 按 🔴 → 🟡 → ⚪ 排序，每项附工作量估级（低/中/高）
5. **快速见效项** — 低成本、高收益的修复

**评分硬规则：**

- 每个评分必须有证据支撑（文件路径 + 行号，或具体观察）。没有证据 → 不评分，写"未评估"而不是猜。
- 只给用户选定的维度打分，未选维度标记"已跳过"。
- 各视图之间、以及视图与模块清单之间必须一致（同一批节点、同一批依赖，外部系统只在系统上下文图里定义一次，见 `mermaid-spec.md` §8），并且 `python check_views.py <源稿.md>` 必须通过。
- 随后按下方"交付流程"处理，保存路径建议 `docs/review/YYYY-MM-DD-<范围>-architecture-review.html`。

### 只出架构文档的变体（不打分）

用户只是想把现有系统的架构写下来时——"帮我梳理这个系统的架构""还原一份架构文档"——不要强行拉着他跑完 8 个维度的深挖：

1. 照常执行第 1 步（项目侦察），并记下取证路径。
2. 跳过第 2 步与第 3 步。
3. 按 `references/review-report-template.md`（对应语言的大纲）产出：第 **2 节 系统架构（现状）**的五类必需视图（以及触发条件成立的条件视图）、模块清单（职责与依赖从代码里读）、能查到的接口定义、只写有仓库依据的 ADR 式决策记录，以及一份简短风险清单。**第 1 节（评分总览表）整节不要**——没做评估就绝不编分数；就算全填"未评估"，页面也不会画雷达图（少于 3 个数字评分即不绘制），留着只是一张废表。
4. 在摘要里明确说明：本次只输出**现状架构文档，未做评分**。
5. 走通用"交付流程"，保存路径建议 `docs/architecture/YYYY-MM-DD-<范围>-architecture.html`。

## 工作流 B：架构设计

### 第 1 步 — 需求澄清

先列出已知需求，再逐条确认模糊点（这就是维度 1——功能正确性——在设计期的应用）。**需求未澄清前不画架构图。** 询问：核心业务流、使用者/角色、预期产出、已知的未来需求。

### 第 2 步 — 约束确认

一次性问清（这些直接决定架构形态）：

| 约束 | 关联维度 |
|------|-----------|
| 目标环境/平台（自建/云/桌面/嵌入式） | 可移植性 |
| 预估数据量与并发（现在与一年后） | 性能/可伸缩性 |
| 安全要求（敏感数据、合规、认证模型） | 安全性 |
| 团队规模与维护能力 | 可维护性、易用性 |
| 需对接的存量系统 | 可维护性 |

### 第 3 步 — 方案权衡

给出 2-3 种候选架构方案（如 单体 / 分层 / 模块化 / 事件驱动 / 微服务——按实际规模选择），用 8 个维度做对比表，给出推荐及理由。用户选定或调整后再输出最终文档。

### 第 4 步 — 输出设计文档

按 `references/design-doc-template.md`（对应语言的大纲）生成，包含：

1. **背景与目标**、2. **需求** —— 问题、目标、非目标、已确认需求
3. **架构视图** —— 按 `mermaid-spec.md` §1 输出**五类必需视图**：系统上下文（边界与外部参与方）、组件图（部件、存储、依赖）、分层图（节点集合必须与组件图相同，含每层职责与允许的依赖方向）、运行时图（主要流程的 `sequenceDiagram`，**必须含失败分支**）、数据流图（边标注数据名，标注存储与信任边界）。再补上所有触发条件成立的条件视图：部署图、状态机图、数据模型。（泳道图按需才出，规则见 mermaid-spec.md §3.4；它只值得画在能画出人工步骤等别的视图画不出来的东西时。）每张图配一句"看图重点"；把分层图并入组件图必须显式说明。
4. **模块清单与职责** —— 每个模块回答：做什么/怎么用/依赖什么
5. **接口定义**（模块级函数/API/事件/数据契约）
6. **ADR 决策记录** —— 每个关键取舍：备选方案、选择、理由、代价
7. **8 维度自检** —— 设计如何满足每个维度；未满足的显式标注为风险
8. **演进路线图** —— 先 MVP，再分阶段演进；避免大爆炸式设计

定稿后：对话中先展示**结构化摘要**（标题、目标/非目标、推荐方案一句话、画了哪些视图、模块与 ADR 清单、自检风险项、路线图阶段），随后按下方"交付流程"处理，保存路径建议 `docs/design/YYYY-MM-DD-<系统>-architecture-design.html`。除非用户要求，不在对话中全文铺 Markdown——完整文档就是那个产物本身。

## 交付流程（工作流 A/B 第 4 步通用）

交付物**就是架构文档**：单文件 HTML，`.md` 源稿作为可选附带产物。

1. **按选定语言写完整文档**（.md 源稿），使用对应语言的模板大纲：所有章节、五类必需视图与所有触发条件成立的条件视图都要有真实内容——绝不是摘要。然后跑视图门禁：`python <技能包 references/html 路径>/check_views.py <源稿.md>`，改到通过为止。
2. **对话里只展示简短结构化摘要**（章节 + 关键结论），不铺全文。
3. **只问一次**（用文档语言问）：
   > "保存为 HTML 文件吗？同时保留 .md 源稿吗？保存到哪里？"
   未经询问绝不保存。若第 0 步的语言还没确定（例如会话中断后又继续），就在这里、**生成之前**补问，并且调用生成器时 `--lang` 必须是显式值。
4. **生成 HTML：**
   - 依次探测解释器：`py -3` / `python3` / `python`（Windows 上 `py -3` 优先）。可用 → **Tier 1**：
     - 把源稿放在输出目录旁，运行：
       `python <技能包 references/html 路径>/md2html.py <源稿.md> <输出.html> --lang <en|zh>`（技能包路径用 glob 从当前项目向上找 `**/references/html/md2html.py`）
     - `--lang` 必须与第 0 步选定的语言一致；它同时本地化 HTML 菜单**和图注**，所以菜单不可能与正文语言不一致
     - 用户要保留 `.md` 时：把源稿写到/留在 HTML 旁的最终 `.md` 路径（同名不同后缀），并用 `--keep-src` 运行；否则转换成功后源稿会被删除
     - 校验产物存在、含 `data-lang="<lang>"`、且不残留 `<!--T:` 令牌
   - 不可用 → **Tier 2**：复制 `references/html/report-shell.html` 为输出文件，设置 `<html lang="…" data-lang="…">`，按 `html-output-spec.md` §10 填充令牌（标题/元信息/正文），删除 `<!--T:EXTRA-->`
5. **按 `html-output-spec.md` §11 清单自查**——重点是：全文一种语言（含菜单）、视图清单齐全且 `check_views.py` 通过、图形可缩放、无残留令牌。
6. 汇报保存路径（HTML，以及保留时的 `.md`）。

## 输出规则

- 评审报告与设计文档的**完整载体是单文件 HTML 架构文档**（自包含、双击可开、菜单与正文同语言、图形可缩放）；对话内只展示结构化摘要。
- `.md` 源稿是**可选的一等产物**，不只是中间文件：用户需要时就与 HTML 同目录、同主文件名保存。
- HTML 遵循 `references/html/html-output-spec.md`；所有内容 Mermaid 图遵循 `references/mermaid-spec.md`（视图清单，以 `.arch` 三件套内嵌源码 + CDN 客户端渲染），并通过 `check_views.py`。
- 生成走双轨：有 Python → `md2html.py --lang` 渲染；无 Python → 按 `report-shell.html` 骨架手写（记得设置 `data-lang`）。两条路径产出同规范产物。
- 每次运行结束时只询问一次："保存为 HTML 文件吗？是否附带 .md 源稿？"——未经询问绝不保存。

## 边界规则

- 大型项目：先划定评审/设计边界，绝不默认全仓库。
- 用户对已有代码的系统要求"设计"：建议先走评审流程，或将现有代码作为设计输入进行评审。
- 纯业务问题或单函数改动：明确说明本技能不适用，直接回答即可。
- 即使在评审/设计之外要求画架构图，mermaid-spec 仍约束图的质量。
- 用户只想要一张图，或只想把已有报告换成另一种语言重出：就只做这件事，不必重跑整个流程（换语言等于用目标语言重写内容，绝不是中英混排打补丁）。

## 每次运行后的自检

- [ ] 先问过（或确认过）文档语言，且**所有内容**——正文、标题、表头、元信息标签、图表标签、图注、HTML 菜单——都是这一种语言
- [ ] 评审报告中每个评分都有证据，没有编造的观察
- [ ] 两种模式都输出五类必需视图 + 所有触发条件成立的条件视图（或写明合并/不适用原因），每张图配一句"看图重点"，且与模块清单一致，`check_views.py` 通过
- [ ] 每张内容 Mermaid 图都符合 mermaid-spec（≤15 节点、一套配色、命名一致、节点 ID 为 ASCII、标签为文档语言、数据流/泳道图的边标注了数据或产物）
- [ ] 设计文档包含模板全部 8 个部分（或显式标注有意省略）
- [ ] 保存产物为 .html 且通过 html-output-spec §11 自查清单（双击可开、`data-lang` 已设置、主题切换、图渲染或降级、缩放/平移/全屏可用、无 `<!--T:` 残留令牌、无 `{}` 占位符）；保存前已询问用户
- [ ] 问题分级统一使用 🔴/🟡/⚪
