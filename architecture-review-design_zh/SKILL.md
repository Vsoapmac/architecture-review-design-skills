# 架构评审与设计

## 概述

本技能包含两种模式：**评审现有架构** 和 **设计新架构**，两者共用一套 8 维度质量框架：

1. **功能正确性** — 模糊的需求能否被精准实现？
2. **可移植性** — 换一个平台/环境，需要改多少代码？
3. **可扩展性 / 可维护性** — 新功能/新业务/业务调整需要改几个文件？
4. **可观测性** — 半夜出问题，多快能定位到？
5. **可测试性** — 功能拆开来测试方不方便？
6. **易用性** — 新人接手，10 分钟内能跑通核心流程吗？
7. **性能 / 可伸缩性** — 数据量/并发量翻 10 倍，架构会变形吗？
8. **安全性** — 发生安全泄露或攻击，影响面多大？

评审模式：先对话式深入，再输出打分报告；设计模式：以需求澄清为驱动，输出完整设计文档。两种模式共享相同的维度定义和 Mermaid 架构图规范。

## 何时使用

| 场景 | 示例触发语 |
|------|-----------|
| 评审现有代码库 | "架构评审"、"评审一下这个项目的架构"、"架构体检"、"帮我看看这个架构" |
| 设计新系统 | "架构设计"、"帮我设计系统架构"、"帮我设计一个 xxx 系统" |
| 评审设计方案 | "这个设计方案靠谱吗"、"帮我评估一下这份设计" |

不适用场景：纯业务问题、单函数改动、文件级别的代码评审（见"边界规则"）。

## 共享基础（任何流程开始前先读）

开始任何评审或设计之前，先读取：

1. **`references/8-dimensions.md`** — 8 个维度的权威定义：核心问题、评估问题集、检查要点、常见反模式、整改建议，以及 0-5 分评分规则。
2. **`references/mermaid-spec.md`** — 图型选型、命名规范、分层配色、节点数量限制、一致性规则。输出任何架构图都必须遵守。

不要凭记忆编造维度定义——一律以参考文件为准。

## 工作流 A：架构评审

### 第 1 步 — 项目侦察

扫描项目：目录结构、README、配置文件、依赖清单、主要源码分布。大型项目先让用户划定评审范围（单文件、单模块或某个子系统）。不要默认全仓库扫描。

### 第 2 步 — 维度裁剪

询问用户哪些维度最重要。默认跑全部 8 个，但允许裁剪——例如小型命令行工具可以跳过"性能/可伸缩性"。深入前先确认最终维度清单。

### 第 3 步 — 对话式深挖（一次一个维度）

对每个选定维度：

1. 先问用户的主观感受："维度 X，你觉得有没有隐患？"——先收集用户的视角。
2. 再用 `8-dimensions.md` 中该维度的检查要点，结合代码/文档找证据。
3. 逐条讨论发现的问题，并分级：
   - 🔴 **必须修复** — 阻碍正确性、安全性或后续开发
   - 🟡 **建议修复** — 明显痛点，成本中低
   - ⚪ **仅供参考** — 信息性，可选
4. 当前维度讨论完再进入下一个。不要一次性倾倒所有发现。

### 第 4 步 — 打分报告

所有维度讨论完毕后，按 `references/review-report-template.md` 汇总成报告：

- 8 维度雷达总览表（每项 0-5 分 + 一句话结论）
- 各维度详情：评分、证据（文件路径/行号/代码片段）、问题清单及优先级
- 整改路线图：按 🔴 → 🟡 → ⚪ 排序，每项附工作量估级（低/中/高）

**评分硬规则：**

- 每个评分必须有证据支撑（文件路径 + 行号，或具体观察）。没有证据 → 不评分，写"未评估"而不是猜。
- 只给用户选定的维度打分，未选维度标记"已跳过"。
- 报告展示完后，询问是否保存为文件（建议 `docs/review/YYYY-MM-DD-<范围>-architecture-review.md`）。

## 工作流 B：架构设计

### 第 1 步 — 需求澄清

先列出已知需求，再逐条确认模糊点（这就是维度 1——功能正确性——在设计期的应用）。**需求未澄清前不画架构图。** 询问：核心业务流、使用者/角色、预期产出、已知的未来需求。

### 第 2 步 — 约束确认

一次性问清（这些直接决定架构形态）：

| 约束 | 关联维度 |
|------|-----------|
| 目标环境/平台（自建/云/桌面/嵌入式） | 可移植性 |
| 预估数据量与并发（现在与一年后） | 性能/可伸缩性 |
| 安全要求（敏感数据、合规、认证模型） | 安全性 |
| 团队规模与维护能力 | 可维护性、易用性 |
| 需对接的存量系统 | 可维护性 |

### 第 3 步 — 方案权衡

给出 2-3 种候选架构方案（如 单体 / 分层 / 模块化 / 事件驱动 / 微服务——按实际规模选择），用 8 个维度做对比表，给出推荐及理由。用户选定或调整后再输出最终文档。

### 第 4 步 — 输出设计文档

按 `references/design-doc-template.md` 生成：

1. 概览 + Mermaid 架构图（组件图/流程图，遵循 `mermaid-spec.md`）
2. 模块清单与职责——每个模块回答：做什么/怎么用/依赖什么
3. 接口定义（模块级函数/API/事件）
4. ADR 决策记录——每个关键取舍：备选方案、选择、理由、代价
5. 8 维度自检表——设计如何满足每个维度；未满足的显式标注为风险
6. 演进路线图——先 MVP，再分阶段演进；避免大爆炸式设计

文档默认在对话中展示，结尾询问是否保存到 `docs/design/`。

## 输出规则

- 报告和设计文档**默认在对话中输出**。
- 每次运行结束时询问一次："需要保存成文件吗？"——未经询问绝不保存。
- 所有架构图必须是 Mermaid，且遵循 `references/mermaid-spec.md`。

## 边界规则

- 大型项目：先划定评审/设计边界，绝不默认全仓库。
- 用户对已有代码的系统要求"设计"：建议先走评审流程，或将现有代码作为设计输入进行评审。
- 纯业务问题或单函数改动：明确说明本技能不适用，直接回答即可。
- 即使在评审/设计之外要求画架构图，mermaid-spec 仍约束图的质量。

## 每次运行后的自检

- [ ] 评审报告中每个评分都有证据，没有编造的观察
- [ ] 每张 Mermaid 图都符合规范（≤15 节点、分层配色、命名一致）
- [ ] 设计文档包含全部 6 个必需部分（或显式标注有意省略）
- [ ] 保存任何文件前都询问过用户
- [ ] 问题分级统一使用 🔴/🟡/⚪
