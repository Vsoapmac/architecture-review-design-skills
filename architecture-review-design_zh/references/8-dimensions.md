# 8 维度架构质量框架

本技能评审与设计工作流共用的 8 个质量维度的唯一权威来源。

## 评分规则（适用于每次评审）

- 评分范围：**0-5 分**。含义：0 = 缺失/已坏，1 = 勉强存在，2 = 较弱，3 = 可接受，4 = 良好，5 = 标杆。
- **每个评分必须有证据**——文件路径 + 行号、具体代码片段、或侦察阶段的直接观察。没有证据 → 写"未评估"，不要编造分数。
- 只给用户选定的维度评分，其余标记"已跳过"。
- 维度评分评价的是**当前状态**，不是路线图。整改方案单独列出。

---

## 1. 功能正确性

**核心问题：** 模糊的需求能否被精准实现？（一个含糊的需求能否变成可运行、可验证的功能？）

### 评估问题集
1. 需求记录在哪里（文档/工单/注释），每个功能能否追溯到一条需求？
2. 实现前是否定义了验收标准，还是"跑通一次"就算完成？
3. 用户说"灵活处理"时——边界情况（空输入、错误格式、超时）的实际行为有定义吗？
4. 业务规则有唯一事实来源，还是散落在多个模块里？
5. 失败路径有规定吗（某一步失败时必须发生什么），还是只写了正常路径？

### 检查要点
- 需求文档 vs 代码：挑 2-3 个功能，验证 需求 → 测试 → 实现 的链条
- TODO、"临时方案"之类的注释和魔法行为
- 核心流程的异常/错误处理覆盖情况
- 业务规则是否以不同取值重复出现在多个文件中

### 常见反模式
- 不确认需求，凭假设直接实现
- 验收标准 = "打印出了预期输出"
- 边界条件静默跳过或统一抛出通用异常
- 业务规则复制多份，各份之间逐渐漂移
- 没有行为*为什么*存在的记录（决策不可追溯）

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 为最重要的 3 条流程补写验收标准；补充边界用例测试 |
| 中 | 把重复的业务规则集中到一个模块；建立功能 → 文件的需求索引 |
| 高 | 引入需求跟踪（每个功能一条工单）并为新工作建立追溯表 |

## 2. 可移植性

**核心问题：** 如果换一个平台/环境，需要改多少代码？

### 评估问题集
1. 代码或配置里有没有硬编码的绝对路径、IP、端口、机器名？
2. 环境差异（操作系统、路径、编码、换行符）是显式处理还是默认假设？
3. 配置是外部化的（环境变量/配置文件），还是编译进了代码？
4. 依赖是否锁定版本（lock 文件）？
5. 应用是否假设了特定工作目录或文件系统布局？
6. 有没有未抽象的平台相关调用（仅 Windows API、unix 语法 shell 命令）？

### 检查要点
- 搜索绝对路径、硬编码 `localhost:port`、`C:\`、`/home/` 等模式
- 配置文件 vs 代码常量；是否有 `.env.example` / 配置模板
- 锁文件（`requirements.txt` 带版本、`package-lock.json`、`poetry.lock` 等）
- `os.path` vs `pathlib`、字符串拼接路径、`os.system` 调用
- 文件 I/O 的编码假设（GBK vs UTF-8）

### 常见反模式
- 配置值嵌在源码里
- 路径用硬编码分隔符拼接，或依赖当前工作目录
- 不锁定依赖版本 →"在我机器上能跑"
- 仅 Windows 兼容的代码且无回退
- 默认编码假设（跨操作系统 locale 直接挂）

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 把硬编码的路径/IP/端口提取到配置；添加 `.env.example` |
| 中 | 全面改用 `pathlib.Path`；锁定依赖；添加 devcontainer 或初始化脚本 |
| 高 | 平台相关调用抽象为接口；在第二个平台上跑 CI |

## 3. 可扩展性 / 可维护性

**核心问题：** 新功能或业务调整来了，要改几个文件？

### 评估问题集
1. 模块边界是按业务概念划分的，还是按实现方便划分的？
2. 每个模块能否不读内部实现就回答：做什么/怎么用/依赖什么？
3. 加一个新功能需要改哪些文件？（答案应该是"一个模块 + 它的测试"，而不是"5 个分散的文件"）
4. 有没有必须手动保持同步的重复逻辑？
5. 最大的文件有多大，是否一个文件承担多个职责？
6. 模块内部实现能否改动而不影响调用方？

### 检查要点
- 核心包内文件大小与类/函数数量
- 跨文件复制的代码块（搜索重复签名）
- 耦合味道：A 模块深挖 B 模块的内部实现
- 命名：按层命名（`utils.py`、`common.py`）vs 按业务概念命名
- 上帝对象：一个类承担 10+ 职责

### 常见反模式
- `utils.py` / `common.py` / `helpers.py` 大杂烩
- 加一个功能要改 5+ 个不相关文件
- 业务逻辑写在 UI 层/入口代码里
- 复制粘贴式维护（"改了一处，另一处忘了"）
- 共享可变全局状态导致紧耦合

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 按职责拆分超大文件；重复常量集中到一处 |
| 中 | 按业务概念提取模块并明确公共 API；把业务逻辑从入口文件迁出 |
| 高 | 模块间引入显式接口；消除共享全局状态；硬编码依赖改为依赖注入 |

## 4. 可观测性

**核心问题：** 半夜出问题了，多快能定位到根因？

### 评估问题集
1. 系统有日志吗？是结构化日志（级别、时间戳、上下文）还是裸 `print`？
2. 单次请求/业务流能否端到端追踪（请求 ID / 链路 ID）？
3. 关键指标有采集吗（延迟、错误率、队列深度、资源占用）？
4. 有告警吗，还是靠人肉发现？
5. 日志去向：轮转、留存、可搜索，还是写进没人看的文件？
6. 失败任务能否与慢任务、重试任务、成功任务区分开？

### 检查要点
- 日志语句：带上下文（ID、参数）还是只有静态字符串？
- 日志配置：级别可通过环境变量配置？stdout vs 文件？轮转？
- 监控/告警配置是否存在（看板、告警规则）
- 错误处理：是否在失败点记录了异常和导致失败的载荷？
- 启动/错误事件是否记录，还是静默？

### 常见反模式
- 只有 `print`，或全部 INFO 不分区级别
- 异常被吞掉（`except: pass`）或记录时不带异常
- 跨模块没有请求/事务 ID
- 日志没有时间戳，或只有本地时间
- 成功与失败在日志里无法区分
- 没有告警——靠用户发现

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 统一日志格式（时间戳+级别+记录器+消息）；异常记录完整堆栈 |
| 中 | 引入请求 ID 并在调用链中传递；配置日志轮转与留存 |
| 高 | 结构化日志 + 指标端点 + 针对错误率和延迟的基础告警规则 |

## 5. 可测试性

**核心问题：** 这个功能拆开来测试方不方便？

### 评估问题集
1. 核心逻辑能否不依赖外部（数据库、网络、文件系统、时间）运行？
2. 依赖是注入的，还是在被测代码内部 new 出来的？
3. 有单元/集成测试，还是只靠手工测试？
4. 测试一个模块是否必须先搭好完整环境？
5. 测试是确定性的（不依赖时间/随机数/网络）且快速的吗？
6. 测试金字塔是否成立（大量快速单元测试，少量慢集成测试）？

### 检查要点
- 测试目录，核心业务逻辑的覆盖情况
- 依赖在函数内创建 vs 注入
- 测试搭建复杂度（一个测试是否需要真实数据库在跑）
- 业务逻辑里出现 `time`、`random`、网络调用（难以测试）
- 测试运行时长（跑一次 20 分钟的测试套件没人愿意跑）

### 常见反模式
- 业务逻辑与 I/O 纠缠，每个测试都要真实环境
- 核心流程零测试，"我们手工测试"
- 测试依赖墙钟时间或随机值
- 测试结果取决于运行顺序或机器
- 没有任何测试替身（mock/stub），只有全链路测试

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 为最关键的 3 个纯函数补单元测试；在 README 写明测试命令 |
| 中 | 抽出 I/O 边界，核心逻辑改为注入依赖；补充集成测试环境 |
| 高 | 全量依赖注入重构；建立快速单元测试层和 CI 测试门禁 |

## 6. 易用性

**核心问题：** 新人接手，10 分钟内能跑通核心流程吗？

### 评估问题集
1. README 是否包含：前置条件、安装步骤、运行步骤、配置说明？
2. 一条文档化的命令能否完成启动，包括环境准备（依赖、配置、数据库）？
3. 有示例输入/样例吗，让用户能立即跑通正确路径？
4. 错误信息是否可行动（"请设置环境变量 X"），而不是晦涩堆栈？
5. 测试/演示有样例数据吗，还是必须用生产数据？
6. 首次体验如何——clone → 读文档 → 运行，还是反推代码一天？

### 检查要点
- README 完整度（安装/运行/配置章节）
- 一条命令完成环境搭建（Makefile、脚本、包管理器 scripts）
- 默认配置开箱即用 vs 需要领域知识
- `input/` / `examples/` 中有示例输入
- 最常见错误场景的错误处理质量

### 常见反模式
- README 缺失或只有一行"很简单的"
- 环境搭建需要未文档化的手工步骤（建库、设置 10 个没人知道的环境变量）
- 没有样例数据；首次运行需要生产数据或现编数据
- 错误只给堆栈，不给操作者提示
- 前置条件靠猜（Python 3.9 vs 3.11、Node 版本、数据库版本）

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 写 README 的安装/运行章节；加一个示例输入；修复最让人困惑的错误提示 |
| 中 | 提供一键环境搭建脚本和样例数据；文档化配置项及默认值 |
| 高 | 提供容器化/devcontainer 方案；自动化冒烟测试作为入职检查 |

## 7. 性能 / 可伸缩性

**核心问题：** 数据量或并发量翻 10 倍，架构会变形吗？

### 评估问题集
1. 10 倍数据量下会发生什么：瓶颈在哪（数据库查询、循环、I/O）？
2. 昂贵操作是否明显（N+1 查询、全表扫描、热路径上的阻塞调用）？
3. 计算/worker 能水平扩展吗（无状态或可分区），还是有单点争用？
4. 任何地方有容量数字吗（预期用户数、行数、请求/秒）？
5. 数据存储方式是否匹配访问模式（索引、反规范化、缓存）？
6. 并发处理正确吗（共享状态、竞态条件、连接池）？

### 检查要点
- 查询：循环内调用数据库/HTTP、缺索引
- 请求路径上的同步阻塞调用
- 全局锁、单 worker 假设、无锁共享内存状态
- 批处理任务把全部数据读进内存
- 是否有文档化的容量估算或压测结果

### 常见反模式
- "我的测试数据能跑通"——从不考虑负载
- 列表/导出流程中的 N+1 查询
- 为了"简单"全部在内存里处理
- 单实例假设写死（本地文件、进程内状态）
- 热点且昂贵的数据没有任何缓存
- 任何地方都没有容量数字——答不出"什么先坏？"

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 修明显的热点（索引、N+1、热门数据加缓存）；用简单基准测试量化 |
| 中 | 让 worker 无状态/可分区；重活引入队列；加分页/批量处理 |
| 高 | 由实测瓶颈驱动的架构调整（异步处理、水平扩展、只读副本、缓存层） |

## 8. 安全性

**核心问题：** 发生安全泄露或攻击，影响面有多大？

### 评估问题集
1. 敏感数据存在哪（机密、凭据、PII），谁能访问？
2. 所有输入都经过校验吗（API 参数、文件内容、用户输入字符串）？
3. 机密在代码里、提交进仓库的配置里，还是由正规机制管理？
4. 权限模型如何——每个模块最小权限，还是一个超级凭据到处用？
5. 攻击面明确吗：哪些端点/文件/命令接受外部输入？
6. 一个组件被攻破后能触达一切，还是被隔离？

### 检查要点
- 源码、配置文件或提交历史中的机密/凭据
- 所有外部边界（API、CLI 参数、文件解析）的输入校验
- 授权：只有认证（authN），还是也有授权（authZ）？
- SQL/命令构造：字符串拼接 vs 参数化查询
- 日志中的敏感数据（密码、令牌、PII 出现在日志行）
- 网络暴露面：什么在监听，从哪里可达

### 常见反模式
- 密码/API 密钥提交进仓库或硬编码
- 不做输入校验（"内部工具，不用"）
- 所有模块共用一个管理员凭据
- 用用户输入拼接 SQL/shell 命令
- 日志整包输出敏感载荷
- 没有最小权限概念，一切以 root/admin 运行

### 整改建议
| 成本 | 动作 |
|---|---|
| 低 | 机密迁到环境变量/密钥管理；移除硬编码凭据；外部边界校验输入 |
| 中 | 查询/命令参数化；日志脱敏敏感字段；凭据按最小权限收敛 |
| 高 | 引入授权模型、密钥轮换、输入校验中间件，并对暴露面做威胁评审 |
