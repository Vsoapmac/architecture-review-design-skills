# 架构设计文档模板

每个部分都要填充真实内容，不要保留占位文字。`{花括号}` 内的占位符必须替换或删除。所有图遵循 `mermaid-spec.md`。
> **本文档双重职责:** ① 对话"结构化摘要"的章节大纲;② Tier 1 的 .md 源稿写作大纲(md2html.py 依赖各 h2 标题做组件映射,见 `html/html-output-spec.md` §4)。**修改 h2 标题必须同步 html-output-spec.md 的映射表。**

```markdown
# 架构设计：{系统名称}

- **日期：** {YYYY-MM-DD}
- **作者：** {谁}
- **状态：** 草稿 / 已批准

## 1. 背景与目标

- **问题陈述：** {该系统要解决的问题，2-3 句话}
- **目标：** {必须达成的结果，编号列表}
- **非目标：** {明确排除在外的内容——防止范围蔓延}

## 2. 需求（已与干系人确认）

- **功能需求：** {已确认的核心流程，每条带验收标准}
  - {流程 1}：{验收标准}
  - {流程 2}：{验收标准}
- **约束：** {目标平台、数据量/并发预估、安全要求、团队规模}
- **假设：** {假定成立的事实，便于日后重新审视}

## 3. 架构概览

{Mermaid 组件图，遵循 mermaid-spec.md —— 层次：入口 / 服务 / 数据 / 外部}

### 关键流程：{核心场景 1}
{最重要的运行时路径的 Mermaid 时序图}

### 关键流程：{核心场景 2}
{第二条重要路径的 Mermaid 时序图（如有）}

## 4. 模块清单与职责

每个模块回答：做什么 / 怎么用 / 依赖什么。

| 模块 | 职责 | 公共入口（怎么用） | 依赖 |
|---|---|---|---|
| {模块名} | {做什么} | {API/函数/事件} | {依赖的模块} |
| ... | | | |

## 5. 接口定义

### 模块级 API
- `{模块}.{函数}({参数}) -> {返回值}` — {一句话语义，错误行为}

### 事件 / 消息（如有）
- `{事件名}` — {发布者} → {订阅者}，载荷 `{结构}`，投递保证 `{至少一次/恰好一次/尽力而为}`

### 数据契约（如适用）
- {实体}：{关键字段、约束} — 归属 {模块}

## 6. ADR 决策记录

每个关键决策一个区块，按决策日期排序。

### ADR-{n}：{决策标题}

- **日期：** {YYYY-MM-DD}
- **状态：** 已接受 / 已被 ADR-{m} 取代
- **背景：** {该决策要解决的问题}
- **备选方案：** {方案 A — 优缺点；方案 B — 优缺点}
- **决策：** {被选中的方案}
- **理由：** {为什么选中它}
- **后果 / 代价：** {该决策日后需要付出的成本}

## 7. 8 维度自检表

设计如何满足每个维度。未满足的项是风险，不是遗漏。

| 维度 | 设计如何应对 | 状态 |
|---|---|---|
| 1. 功能正确性 | {需求 → 模块映射，验收标准覆盖} | ✅ / ⚠️ 风险 |
| 2. 可移植性 | {配置外部化，环境假设} | ✅ / ⚠️ 风险 |
| 3. 可扩展性 / 可维护性 | {模块边界，新功能预期改动的文件范围} | ✅ / ⚠️ 风险 |
| 4. 可观测性 | {本设计的日志/链路/指标/告警方案} | ✅ / ⚠️ 风险 |
| 5. 可测试性 | {依赖注入，各模块测试策略} | ✅ / ⚠️ 风险 |
| 6. 易用性 | {上手故事、文档、样例数据计划} | ✅ / ⚠️ 风险 |
| 7. 性能 / 可伸缩性 | {容量估算，10 倍数据下的瓶颈分析} | ✅ / ⚠️ 风险 |
| 8. 安全性 | {输入校验、机密管理、最小权限、影响面} | ✅ / ⚠️ 风险 |

**需跟踪的已知风险：** {所有 ⚠️ 项，各展开一行}

## 8. 演进路线图

分阶段推进，MVP 先行。每个阶段独立产生价值。

| 阶段 | 范围 | 退出标准 |
|---|---|---|
| MVP | {最小可用纵向切片} | {必须跑通什么} |
| 阶段 2 | {下一增量} | {必须跑通什么} |
| 阶段 3 | {后续增长} | {必须跑通什么} |

**明确推迟：** {本设计刻意不做的事，附重新审视的触发条件}
```
