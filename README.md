# 架构评审与设计 (architecture-review-design)

## 一、这个 SKILL 是什么

### 1.1 定义

架构评审与设计是一套基于 **8 个质量维度** 的系统化架构工作流，主要定义了三件事：

- **评审模式**：对现有代码库/架构按 8 个维度逐一体检，对话式深挖 + 证据驱动的打分报告，**并还原出这个系统"现状（As-Is）"的架构文档**
- **设计模式**：从需求澄清到完整设计文档（四类架构视图、模块清单、接口定义、ADR、自检表、演进路线图）
- **交付形态**：交付物**就是架构文档本身**——单文件 HTML（自包含、双击可开、图形可缩放），`.md` 源稿可选附带

核心框架 —— 8 个维度（源于 8 个经典架构问题）：

| # | 维度 | 核心问题 |
|---|------|----------|
| 1 | 功能正确性 | 模糊的需求能否被精准实现？ |
| 2 | 可移植性 | 换一个平台/环境，需要改多少代码？ |
| 3 | 可扩展性 / 可维护性 | 新功能/业务调整需要改几个文件？ |
| 4 | 可观测性 | 半夜出问题，多快能定位到？ |
| 5 | 可测试性 | 功能拆开来测试方不方便？ |
| 6 | 易用性 | 新人接手，10 分钟内能跑通核心流程吗？ |
| 7 | 性能 / 可伸缩性 | 数据量/并发量翻 10 倍，架构会变形吗？ |
| 8 | 安全性 | 发生安全泄露或攻击，影响面多大？ |

**五类必需架构视图**（评审与设计都要齐全，每张图回答一个问题）：

| 视图 | 回答的问题 | 读图要点 |
|------|-----------|---------|
| 系统上下文图 | 系统边界在哪、外部参与者是谁、进出什么 | 外部系统是否只在这里定义一次 |
| 组件图（架构图） | 系统由哪些部件组成、谁依赖谁 | 拓扑完整性、与模块清单是否一致 |
| 分层图（分层视图） | 每层放什么职责、允许谁调谁 | 依赖方向是否越层；**节点集合必须与组件图完全相同** |
| 运行时图（时序图） | 一次请求/事件跨模块怎么走、同步还是异步 | 调用方在哪停止等待；**必须含失败分支** |
| 数据流图（DFD） | 数据从哪来、经谁处理、存到哪、流向哪里 | 每条边标注数据名；跨了哪条信任边界、谁拥有哪个存储 |

**三类按触发条件画的视图**（触发条件是系统的事实，不是偏好）：

| 视图 | 什么时候必须画 |
|------|---------------|
| 部署图 | 多节点/多区域/多环境 |
| 状态机图 | 核心实体 ≥4 个状态，或存在状态相关规则 |
| 数据模型（ERD） | 数据模型是主要耦合点（共享库、多消费方） |

> **泳道图不在清单里，按需才出**（你明确要才画，规则仍保留在 mermaid-spec.md §3.4）。原因很实在：服务到服务的流程，时序图说得更准；Mermaid 没有原生泳道语法（只能用 `flowchart` + subgraph 硬凑，排版会被渲染器重排）；而且和时序图并行维护是同一条流程写两遍，是漂移的来源。它真正不可替代的场景只有一个——**要画出人工步骤、系统外绕行、跨团队责任**（比如"值班工程师手工改库"），这时它会值回票价，否则就别画。

> **分层图与组件图不是同一种东西**：组件图看拓扑，分层图看职责归位与依赖方向——它是组件图的受约束特化，所以**两者节点集合必须相同**，只是排列方式不同。系统确实很小时可把分层图并入组件图，但必须写明合并原因；画不出的必需视图保留标题写一行"不适用的原因"——**不允许默不作声地省略**。
>
> **视图之间必须自洽**，而且这件事是可执行的：`python check_views.py <源稿.md>` 会检查五类视图是否齐全、分层图与组件图节点集合是否一致、外部系统是否只在上下文图定义一次、数据流/泳道图的边是否标注了数据、存储是否有人读也有人写、运行时图是否有失败分支、单图节点是否超过 15 个等。**图与文冲突时先改图再读文**，不能任由图文互相矛盾。

### 1.2 什么时候会用到它 🎯

**架构评审（存量系统体检）**
想评估现有项目质量、定位隐患、拿到"现状架构文档 + 整改路线"时。比如"帮我评审一下这个项目的架构"。

**架构设计（新系统从零开始）**
动手写代码之前需要一份靠谱的设计方案时。比如"帮我设计系统架构"。

**设计方案把关**
已经有了一份设计或方案，想验证它靠不靠谱时。

### 1.3 谁适合用 👥

- 技术负责人/架构师：给团队定架构标准，评审时输出能对齐的结论
- 开发者：设计新模块、评估老代码时多一双专业的眼睛
- 技术咨询/外包：快速给客户输出结构化的架构评估报告
- 用 AI 辅助开发的团队：让 AI 按统一框架做架构工作，而不是每次风格不同

## 二、为什么要用它

### 2.1 之前是怎么做的 😅

**评审时：**
- 凭感觉看代码，"感觉这个模块有点乱"，说不出乱在哪、影响多大
- 发现的问题散落在对话里，没有优先级、没有证据、没有整改路线
- 评审结论无法量化，汇报时拿不出东西
- 想要一份"这个系统现在长什么样"的架构图，得自己从头画

**设计时：**
- 需求还没澄清就急着画图，画完发现方向错了
- 架构图随手画，格式混乱、没人看得懂、跟代码对不上
- 设计做完没有记录，为什么这么取舍，三个月后没人记得
- 图里部件一多就糊成一团，报告里放大了也看不清

### 2.2 用了之后怎么样 ✨

**评审：**
- 8 个维度逐一体检，每个评分都有证据（文件路径 + 行号），不拍脑袋
- 发现的问题分级 🔴 必须修 / 🟡 建议修 / ⚪ 仅供参考，附整改路线和成本
- 对话式深入，先听你的判断，再结合证据补充，而不是 AI 单方面下结论
- 交付物是"现状架构文档 + 评分报告"：五类必需视图由代码还原，每张都注明取证来源，缺陷在正文点名

**设计：**
- 需求澄清不完成不画图，杜绝方向性返工
- 视图清单齐备（五类必需 + 触发条件成立的条件视图），统一规范（一套配色、≤15 节点、ID 用英文、标签用文档语言），并由 `check_views.py` 校验视图之间的一致性
- 模板 8 节齐备（背景与目标、需求、架构视图、模块清单、接口定义、ADR、8 维自检表、演进路线图），一键输出自包含 HTML
- 每次关键取舍都有 ADR 记录，决策可追溯

**交付与阅读体验：**
- **语言一次问清**：动手前先问"中文 / English"，正文、图表标签、表头、图注、**HTML 菜单**全部同一种语言，不可能再出现"正文中文、菜单英文"
- **图片可自由缩放**：每张图右上角有缩放条（`−` / 百分比 / `＋` / `⟲` 复位 / `⛶` 全屏），支持 Ctrl/⌘+滚轮缩放、拖动平移、双击放大、全屏查看，打印时自动复位
- **`.md` 源稿可选保留**：需要就拿去入库、进 Git、喂给其他工具

### 2.3 对比一下 📊

| 方面 | 用之前 | 用之后 |
|------|--------|--------|
| 评审结论 | 凭感觉，无法量化 | 8 维打分 + 证据 + 整改路线 |
| 问题定位 | 靠经验盲扫 | 按维度逐项检查要点找证据 |
| 架构图 | 随手画，风格不一、跟代码对不上 | 视图清单 + Mermaid 规范统一，且视图间一致性可自动校验 |
| 设计方向 | 需求未澄清就画图 | 澄清 → 约束 → 权衡 → 文档 |
| 决策记录 | 存在对话里，易丢失 | ADR 结构化记录 |
| 新人接手 | 看不懂架构，问东问西 | 文档 + 五类视图 + 决策记录一站式 |
| 交付语言 | 正文中文、菜单英文 | 一次问清，全文（含菜单）统一 |
| 图看不清 | 只能放大浏览器 | 图内缩放/平移/全屏，打印自动复位 |
| 产物形态 | 只有一段对话结论 | 单文件 HTML 架构文档 + 可选 .md 源稿 |

## 三、怎么使用

### 3.1 快速上手三步走 🚀

**第一步：安装 skill（一次性）**

把本仓库克隆到本地，然后在**本仓库的上一级目录**（脚本与各技能仓库同级，即 `F:\code\skills\` 这类布局）执行 `copy-skills-dsh.ps1`（DeepSeek Harness）或 `copy-skills.ps1`（opencode）把技能分发到技能目录：

```bash
powershell -ExecutionPolicy Bypass -File ..\copy-skills-dsh.ps1
```

> 脚本会扫描同级的所有技能仓库；`_zh` 目录是中文副本，与英文版**技能名相同**，默认会被跳过；同一次安装只会生效一份。两份的引擎文件（生成器、HTML 骨架、规范、模板、测试）完全一致，只有 `SKILL.md` 的说明语言和 `references/8-dimensions.md` 的正文语言不同——**语言本身在运行时询问决定**，不依赖装哪一份。

**第二步：触发评审**

在任意项目里说：

```
帮我评审一下这个项目的架构
```

AI 会按流程执行：**语言确认** → 项目侦察 → 维度裁剪 → 对话式深挖 → 打分报告 + 现状架构（五类视图）→ 视图自检 → 交付 HTML。

**第三步：触发设计**

对还没有代码的新系统说：

```
帮我设计一个 xxx 系统的架构
```

AI 会按流程执行：**语言确认** → 需求澄清 → 约束确认 → 方案权衡 → 输出设计文档（五类视图 + 按条件的视图 + 8 节）。

### 3.2 触发词速查 🔑

| 场景 | 触发语 |
|------|--------|
| 评审 | "架构评审"、"评审架构"、"架构体检"、"帮我看看这个架构"、"architecture review" |
| 设计 | "架构设计"、"设计架构"、"帮我设计系统架构"、"architecture design" |
| 方案把关 | "这个设计方案靠谱吗"、"帮我评估一下这份设计" |
| 只梳理现状架构（不打分） | "帮我梳理这个系统的架构"、"还原一份架构文档" |

### 3.3 第 0 步：语言确认 🌐（新增）

动手之前 AI 会先问一句：

> "文档用什么语言？中文 / English（将统一用于正文、图表标签、表格与 HTML 菜单）"

选定的语言贯穿全流程：

- 正文、标题、表头、元信息标签、图注
- Mermaid 图的节点标签 / 连线标签（画泳道图时含泳道名；节点 **ID** 保持英文，便于版本化）
- **HTML 界面菜单**：折叠/展开、搜索框、目录、回到顶部、缩放按钮提示、离线降级提示
- 对应的模板大纲（英文 §A / 中文 §B）与生成参数（`md2html.py --lang`）

中途改语言就整份重写，不做中英混排的"补丁"。

### 3.4 评审模式详解 🔍

**第 1 步 项目侦察**：扫描目录结构、README、配置、依赖清单；大型项目先划定评审边界。侦察结果同时喂给打分和现状架构图。

**第 2 步 维度裁剪**：默认 8 个维度全跑，也可以裁剪（比如纯 CLI 工具跳过性能维度）。

**第 3 步 对话式深挖**：一次一个维度。先问你的主观感受，再按检查要点找代码证据，发现问题立即分级：
- 🔴 **必须修复** — 阻碍正确性、安全性或后续开发
- 🟡 **建议修复** — 明显痛点，成本中低
- ⚪ **仅供参考** — 信息性，可选

**第 4 步 打分报告 + 现状架构**：

1. 总览（8 维雷达表，驱动 HTML 里的雷达图）
2. **系统架构（现状）**：系统上下文图、组件图、分层图、运行时图（含失败分支）、数据流图五张必需视图 + 触发条件成立的条件视图（部署 / 状态机 / 数据模型），每张附"看图重点"和取证来源
3. 各维度详情（评分 + 证据 + 问题清单）
4. 整改路线图（🔴 → 🟡 → ⚪，附工作量估级）
5. 快速见效项

> 硬规则：每个评分必须有证据（文件路径 + 行号），没有证据写"未评估"，绝不猜分。

### 3.5 设计模式详解 🏗️

**第 1 步 需求澄清**：逐条确认模糊点，不澄清完毕不画图。

**第 2 步 约束确认**：一次问清目标平台、数据量/并发预估、安全要求、团队规模、存量系统。

**第 3 步 方案权衡**：给出 2-3 种候选方案，用 8 个维度对比，推荐 + 理由。

**第 4 步 设计文档**（模板 8 节，输出为自包含 HTML）：

1. 背景与目标
2. 需求（已与干系人确认）
3. **架构视图**：系统上下文图 / 组件图 / 分层图 / 运行时图 / 数据流图（+ 按条件的部署图、状态机图、数据模型；泳道图按需）
4. 模块清单与职责（做什么 / 怎么用 / 依赖什么）
5. 接口定义（函数 / API / 事件 / 数据契约）
6. ADR 决策记录（备选方案 + 理由 + 代价）
7. 8 维度自检（不满足的显式标注为风险）
8. 演进路线图（MVP → 分阶段演进）

### 3.6 交付流程 📦

1. AI 先按选定语言写出完整文档（.md 源稿），所有章节与视图都是真实内容，不是摘要；随后跑 `check_views.py`，不通过就改图
2. 对话里只展示简短结构化摘要（章节 + 关键结论）
3. **只问一次**："保存为 HTML 文件吗？同时保留 .md 源稿吗？保存到哪里？"
4. 生成 HTML：
   - 有 Python（`py -3` / `python3` / `python`）→ 跑 `md2html.py <源稿.md> <输出.html> --lang <en|zh>`，成功后源稿默认删除；**要保留 `.md` 必须加 `--keep-src`**（并把源稿写到 HTML 旁的目标路径），否则不管源稿放在哪里都会被删掉
   - 没有 Python → 复制 `report-shell.html` 骨架手写填充（记得设置 `data-lang`）
5. 按验收清单自查：**全文一种语言（含菜单）**、四类视图齐全、图形可缩放、无残留令牌

保存路径建议：

- 设计：`docs/design/YYYY-MM-DD-<系统>-architecture-design.html`
- 评审：`docs/review/YYYY-MM-DD-<范围>-architecture-review.html`

| 功能 | 说明 |
|------|------|
| 深浅色主题 | 右上角 🌓，跟随系统 + 手动覆盖并记忆 |
| 目录与折叠 | 左侧目录自动生成，章节可折叠，"折叠全部 / 展开全部" |

### 3.8 常见问题 ❓

**Q: 为什么以前中文文档会出现英文菜单？现在还会吗？**

不会了。语言在第 0 步问清后，生成器会把界面文案（折叠/展开/目录/搜索/缩放/图注等）**直接写进 HTML 文件**，而不是只靠运行时脚本；同时 HTML 根节点带 `data-lang`，脚本按它切换文案。手工写 HTML 时若忘了设置，脚本还会按正文内容自动判定语言兜底。产物里若出现"正文中文 + 英文菜单"被视为不合格，验收清单会拦。

**Q: 评审一个很大的项目，会不会太慢？**

不会。第 2 步维度裁剪和第 1 步边界划定就是干这个的——先确认评审范围，再按维度逐个深挖，不默认全仓库扫描。

**Q: 评分会不会是 AI 拍脑袋给的？**

评分硬规则里写死了：没有证据不评分。每个分数都要对应具体的文件路径 + 行号或直接观察，报告里能看到证据链。

**Q: 视图必须都画吗？会不会画蛇添足？**

五类必需视图各自回答不同问题，是交付契约；三类条件视图在触发条件成立时也要画（多节点部署就画部署图，等等）。确实画不出时保留标题写一行原因，系统很小可以把分层图并入组件图（写明原因）。禁止的是"悄悄少画一张"——而这件事现在由 `check_views.py` 把关，不靠自觉。泳道图属于按需产物：要的话直接说"加一张泳道图"。

**Q: 想看泳道图怎么办？**

直接说"再给我一张泳道图 / 跨职能流程图"。它不在每次必画的清单里，但规则和校验都在（`check_views.py` 依然会检查泳道数、步骤编号、交接产物是否具名）——而且它只在能画出别的视图画不出来的东西时才值得画，否则我会直说不值当。

**Q: 一张图跟另一张图对不上怎么办？**

跑 `python check_views.py <源稿.md>`。它按 mermaid-spec.md §8 的硬规则检查：分层图与组件图节点集合必须相同、外部系统只在上下文图定义一次、数据流图的存储必须出现在组件图里、数据流/泳道图的边必须有数据名、存储不能没人读或没人写、运行时图必须有失败分支。冲突时的处理顺序是**先改图，再读一遍正文**；如果系统真的就是图里那样，正文必须把它写成评审发现，而不是让图文各说各话。

**Q: 我只想要一份"这个系统现在长什么样"的架构文档，不想跑完整评审怎么办？**

走评审流程的**轻量变体**：说一句"帮我梳理这个系统的架构"，AI 只做项目侦察，然后直接输出「现状架构文档」——四张视图 + 模块清单 + 接口定义 + 有依据的 ADR + 风险清单，**不做 8 维度打分**（第 1 节评分表整节不要；就算全填"未评估"也不会出现雷达图，因为少于 3 个数字评分即不绘制），产物同样是单文件 HTML（可选 .md），默认存 `docs/architecture/`。

**Q: 图太密看不清怎么办？**

打开 HTML 后每张图右上角都有缩放条，可以放大到 800%、拖动平移，或点 `⛶` 全屏看；打印时会自动复位成完整图。

**Q: 设计完就能直接照着写代码吗？**

设计文档里的模块清单、接口定义、ADR 可以直接作为编码的输入，配合其他 AI 编码工作流即可开工。

**Q: 一个已有代码的系统，还能走设计模式吗？**

边界规则规定：已有代码的系统要"设计"，AI 会建议先走评审流程，或把现有代码作为设计输入进行评审——避免脱离现实空谈设计。

技能包里保留了两个可执行工具，改完规范/模板/骨架后建议各跑一次：

```bash
cd architecture-review-design/references/html

python check_views.py ../../docs/design/2026-01-01-order-platform.md
```

改动约定：

| 你要改的东西 | 必须同步的地方 |
|--------------|----------------|

| 视图清单、跨视图一致性规则 | `mermaid-spec.md` §1/§8 + `check_views.py` 的检查项 + 两份模板的 §3/§2 子章节编号（三处必须同步） |
| 引擎文件（shell / 生成器 / 视图门禁 / 规范 / 模板） | `_zh` 副本（**直接复制文件同步**，例如 `robocopy <en> <zh> /E /XF SKILL.md 8-dimensions.md`；两个 copy-skills 脚本默认跳过 `*_zh`，不会帮你同步副本） |

## 六、和其他工具规范的关系 🔗

**与代码评审（ai-think-human-code / chinese-code-review）的区别**
代码评审关注文件级别的具体问题（某段代码怎么写更对）；本 skill 关注系统级别的质量属性（这个模块边界对不对、整体可观测性如何）。两者的分级符号（🔴/🟡/⚪）风格一致，可以衔接使用：架构评审发现的问题，可下发到代码评审层面落实。

**与设计流程类技能（brainstorming / writing-plans）的关系**
本 skill 聚焦"架构"这一层的内容和产出物（8 维度框架、四类视图、ADR）；brainstorming 负责需求探索和规格设计，writing-plans 负责落地实施计划。架构设计文档完成后，可以衔接 writing-plans 生成实施计划。

**与项目结构规范（python-project-structure）的关系**
项目结构规范管"文件往哪放"；本 skill 管"系统怎么设计/评估"。设计文档中的模块清单可以直接映射到项目结构规范里 src/{project_name}/ 的包划分。

## 总结

这个 skill 的核心价值就一句话：**让架构评审和设计从"凭感觉"变成"按框架 + 证据驱动"，并交付一份能直接拿给别人看的架构文档** 🎯

它解决的几个实际问题：评审没标准（8 个维度给你标准）、结论没证据（没证据不评分）、架构图不全或不自洽（视图清单 + `check_views.py` 可执行校验）、图看不清（产物自带缩放/全屏）、交付语言不统一（第 0 步问清，正文与菜单一致）、设计不落地（模板 8 节 + 单文件 HTML，可选 .md 源稿）。不管你是给存量系统做体检，还是从零设计一个新系统，都可以用这套流程拿到结构化、可对齐、可追溯的结果。
