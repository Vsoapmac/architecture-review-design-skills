# 架构评审与设计 (architecture-review-design)

## 一、这个 SKILL 是什么

### 1.1 定义

架构评审与设计是一套基于 **8 个质量维度** 的系统化架构工作流，主要定义了两件事：

- **评审模式**：对现有代码库/架构按 8 个维度逐一体检，对话式深挖 + 证据驱动的打分报告
- **设计模式**：从需求澄清到完整设计文档（架构图、模块清单、接口定义、ADR、自检表、演进路线图）

核心框架 —— 8 个维度（源于 8 个经典架构问题）：

| # | 维度 | 核心问题 |
|---|------|----------|
| 1 | 功能正确性 | 模糊的需求能否被精准实现？ |
| 2 | 可移植性 | 换一个平台/环境，需要改多少代码？ |
| 3 | 可扩展性 / 可维护性 | 新功能/业务调整需要改几个文件？ |
| 4 | 可观测性 | 半夜出问题，多快能定位到？ |
| 5 | 可测试性 | 功能拆开来测试方不方便？ |
| 6 | 易用性 | 新人接手，10 分钟内能跑通核心流程吗？ |
| 7 | 性能 / 可伸缩性 | 数据量/并发量翻 10 倍，架构会变形吗？ |
| 8 | 安全性 | 发生安全泄露或攻击，影响面多大？ |

### 1.2 什么时候会用到它 🎯

**架构评审（存量系统体检）**
想评估现有项目质量、定位隐患、给团队出整改路线时。比如"帮我评审一下这个项目的架构"。

**架构设计（新系统从零开始）**
动手写代码之前需要一份靠谱的设计方案时。比如"帮我设计系统架构"。

**设计方案把关**
已经有了一份设计或方案，想验证它靠不靠谱时。

### 1.3 谁适合用 👥

- 技术负责人/架构师：给团队定架构标准，评审时输出能对齐的结论
- 开发者：设计新模块、评估老代码时多一双专业的眼睛
- 技术咨询/外包：快速给客户输出结构化的架构评估报告
- 用 AI 辅助开发的团队：让 AI 按统一框架做架构工作，而不是每次风格不同

## 二、为什么要用它

### 2.1 之前是怎么做的 😅

**评审时：**
- 凭感觉看代码，"感觉这个模块有点乱"，说不出乱在哪、影响多大
- 发现的问题散落在对话里，没有优先级、没有证据、没有整改路线
- 评审结论无法量化，汇报时拿不出东西

**设计时：**
- 需求还没澄清就急着画图，画完发现方向错了
- 架构图随手画，格式混乱、没人看得懂、跟代码对不上
- 设计做完没有记录，为什么这么取舍，三个月后没人记得

### 2.2 用了之后怎么样 ✨

**评审：**
- 8 个维度逐一体检，每个评分都有证据（文件路径 + 行号），不拍脑袋
- 发现的问题分级 🔴 必须修 / 🟡 建议修 / ⚪ 仅供参考，附整改路线和成本
- 对话式深入，先听你的判断，再结合证据补充，而不是 AI 单方面下结论
- 一键汇总成打分报告，可直接分享给团队/领导

**设计：**
- 需求澄清不完成不画图，杜绝方向性返工
- 架构图用统一的 Mermaid 规范（分层配色、≤15 节点、两级图），文档和代码严格一致
- 模板 8 节齐备（背景与目标、需求、架构概览、模块清单、接口定义、ADR、8 维自检表、演进路线图），可一键输出自包含 HTML
- 每次关键取舍都有 ADR 记录，决策可追溯

### 2.3 对比一下 📊

| 方面 | 用之前 | 用之后 |
|------|--------|--------|
| 评审结论 | 凭感觉，无法量化 | 8 维打分 + 证据 + 整改路线 |
| 问题定位 | 靠经验盲扫 | 按维度逐项检查要点找证据 |
| 架构图 | 随手画，风格不一 | Mermaid 规范统一，可版本化 |
| 设计方向 | 需求未澄清就画图 | 澄清 → 约束 → 权衡 → 文档 |
| 决策记录 | 存在对话里，易丢失 | ADR 结构化记录 |
| 新人接手 | 看不懂架构，问东问西 | 文档 + 图 + 决策记录一站式 |

## 三、怎么使用

### 3.1 快速上手三步走 🚀

**第一步：安装 skill（一次性）**

把本仓库克隆到本地，然后执行 copy-skills.ps1 把技能分发到 opencode 的技能目录：

```bash
powershell -ExecutionPolicy Bypass -File .\copy-skills.ps1
```

**第二步：触发评审**

在 opencode 中对任意项目说：

```
帮我评审一下这个项目的架构
```

AI 会按 4 步流程执行：项目侦察 → 维度裁剪 → 对话式深挖 → 打分报告。

**第三步：触发设计**

对还没有代码的新系统说：

```
帮我设计一个 xxx 系统的架构
```

AI 会按 4 步流程执行：需求澄清 → 约束确认 → 方案权衡 → 输出设计文档。

### 3.2 触发词速查 🔑

| 场景 | 触发语 |
|------|--------|
| 评审 | "架构评审"、"评审架构"、"架构体检"、"帮我看看这个架构"、"architecture review" |
| 设计 | "架构设计"、"设计架构"、"帮我设计系统架构"、"architecture design" |
| 方案把关 | "这个设计方案靠谱吗"、"帮我评估一下这份设计" |

### 3.3 评审模式详解 🔍

**第 1 步 项目侦察**：扫描目录结构、README、配置、依赖清单；大型项目先划定评审边界。

**第 2 步 维度裁剪**：默认 8 个维度全跑，也可以裁剪（比如纯 CLI 工具跳过性能维度）。

**第 3 步 对话式深挖**：一次一个维度。先问你的主观感受，再按检查要点找代码证据，发现问题立即分级：
- 🔴 **必须修复** — 阻碍正确性、安全性或后续开发
- 🟡 **建议修复** — 明显痛点，成本中低
- ⚪ **仅供参考** — 信息性，可选

**第 4 步 打分报告**：8 维雷达总览表 + 每维度的证据和问题清单 + 整改路线图。

> 硬规则：每个评分必须有证据（文件路径 + 行号），没有证据写"未评估"，绝不猜分。

### 3.4 设计模式详解 🏗️

**第 1 步 需求澄清**：逐条确认模糊点，不澄清完毕不画图。

**第 2 步 约束确认**：一次问清目标平台、数据量/并发预估、安全要求、团队规模、存量系统。

**第 3 步 方案权衡**：给出 2-3 种候选方案，用 8 个维度对比，推荐 + 理由。

**第 4 步 设计文档**（按模板 8 节输出，保存为自包含 HTML）：

1. 概览 + Mermaid 架构图（含时序图）
2. 模块清单与职责（做什么 / 怎么用 / 依赖什么）
3. 接口定义（函数 / API / 事件）
4. ADR 决策记录（备选方案 + 理由 + 代价）
5. 8 维度自检表（不满足的显式标注为风险）
6. 演进路线图（MVP → 分阶段演进）

> 输出规则：评审报告与设计文档的完整载体是单文件 HTML（自包含、双击可开、双主题/目录/搜索/图表渲染），对话内只展示结构化摘要；结束时 AI 会问一句"保存为 HTML 文件吗？是否附带 .md 源稿？"，未经询问不落盘。

### 3.5 常见问题 ❓

**Q: 评审一个很大的项目，会不会太慢？**

不会。第 2 步维度裁剪和第 1 步边界划定就是干这个的——先确认评审范围，再按维度逐个深挖，不默认全仓库扫描。

**Q: 评分会不会是 AI 拍脑袋给的？**

评分硬规则里写死了：没有证据不评分。每个分数都要对应具体的文件路径 + 行号或直接观察，报告里能看到证据链。

**Q: 设计完就能直接照着写代码吗？**

设计文档里的模块清单、接口定义、ADR 可以直接作为编码的输入，配合其他 AI 编码工作流即可开工。

**Q: 一个已有代码的系统，还能走设计模式吗？**

边界规则规定：已有代码的系统要"设计"，AI 会建议先走评审流程，或把现有代码作为设计输入进行评审——避免脱离现实空谈设计。

设计要点：主文件只做流程编排（精简），8 维度定义和 Mermaid 规范作为共享资产放在 `references/`，评审和设计两种模式共用一份，避免内容重复漂移。

## 五、和其他工具规范的关系 🔗

**与代码评审（ai-think-human-code / chinese-code-review）的区别**
代码评审关注文件级别的具体问题（某段代码怎么写更对）；本 skill 关注系统级别的质量属性（这个模块边界对不对、整体可观测性如何）。两者的分级符号（🔴/🟡/⚪）风格一致，可以衔接使用：架构评审发现的问题，可下发到代码评审层面落实。

**与设计流程类技能（brainstorming / writing-plans）的关系**
本 skill 聚焦"架构"这一层的内容和产出物（8 维度框架、架构图、ADR）；brainstorming 负责需求探索和规格设计，writing-plans 负责落地实施计划。架构设计文档完成后，可以衔接 writing-plans 生成实施计划。

**与项目结构规范（python-project-structure）的关系**
项目结构规范管"文件往哪放"；本 skill 管"系统怎么设计/评估"。设计文档中的模块清单可以直接映射到项目结构规范里 src/{project_name}/ 的包划分。

## 总结

这个 skill 的核心价值就一句话：**让架构评审和设计从"凭感觉"变成"按框架 + 证据驱动"** 🎯

它解决的三个实际问题：评审没标准（8 个维度给你标准）、结论没证据（没证据不评分）、设计不落地（模板 8 节输出物直接指导编码，交付自包含 HTML 报告）。不管你是给存量系统做体检，还是从零设计一个新系统，都可以用这套流程拿到结构化、可对齐、可追溯的结果。
